# End of Day Handoff

Close out a working session so tomorrow starts from a known state instead of archaeology. Three things get lost overnight and each needs different handling:

1. **Work in the repo** that isn't committed or pushed
2. **Ephemeral state outside the repo** — temp dirs, hand-started servers, exported env vars — that a reboot or `/tmp` cleanup destroys
3. **Reasoning** — why a thing was done a particular way, which is the most expensive to reconstruct and the least likely to be written down

> **Project-specific context** (handoff note path, baseline verification command, known ephemeral resources, commit authorisation) should be defined in the project's `CLAUDE.md` under `## Skill Configuration`. Check there first before asking the user.

## Inputs

Check the project's `CLAUDE.md` for defaults, then ask only for what's still missing and actually needed:

- **Handoff note path** — where the note is written. Must be **outside the repo** and **outside any temp directory**. Default: `~/Documents/<project>-handoff-<YYYY-MM-DD>.md`
- **Baseline command** — the project's verification command (test suite, lint, build) and its known-good result, so tomorrow can compare against a number rather than a vibe
- **Ephemeral resources** — services or data the project needs that aren't provisioned automatically (local database, queue, background worker)
- **Commit authorisation** — whether committing and pushing is pre-approved. Default is **no**: present findings and ask

## Steps

### 1. Sweep for work that would be lost

Verify with commands. Do not rely on recollection of what changed — sessions are long and memory of the working tree is unreliable.

```bash
git status --short                          # uncommitted + untracked
git log @{u}..HEAD --oneline 2>/dev/null    # committed but unpushed
git stash list                              # forgotten stashes
git worktree list                           # stray worktrees
git branch -vv                              # branches with no upstream
```

Check **every** repo touched this session, not just the current directory — shared config repos and sibling checkouts are easy to forget.

### 2. Separate real work from incidental churn

Running a test suite, a build, or a dependency install mutates tracked files as a side effect. Committing those pollutes the diff and obscures the actual change. Classify every modified file as **intentional** or **incidental** before proposing anything.

Common incidental churn:
- Lockfiles gaining a platform or hash line from a local install
- Test-runner state files (example status, timing caches, coverage output)
- Schema dumps regenerated by running migrations
- Build output or compiled assets

List the incidental ones with the exact command to revert them and let the user run it. This skill does not modify the working tree — a file you were confident was churn is exactly the file someone spent the afternoon on.

Be careful with the ambiguous case: a regenerated schema dump is *usually* churn, but is a genuine fix when the committed version was wrong. Decide deliberately and say which call was made.

### 3. Propose, don't commit

Present the classification and let the user decide. **Never commit or push as a side effect of housekeeping** — an end-of-day sweep is the worst moment to make an unreviewed commit, because nobody is watching and the reasoning isn't fresh tomorrow.

If the work isn't ready to commit, that is fine and normal. Leave it uncommitted and describe it in the note. Uncommitted work that is *written down* is not lost work.

If `## Skill Configuration` pre-authorises committing, still report exactly what was committed and where.

### 4. Catalogue ephemeral state — and prefer fixing it to documenting it

Identify anything the session depends on that won't survive the night:

```bash
pgrep -fl "<hand-started service>"    # background processes still running
ls -d /tmp/* 2>/dev/null              # temp artifacts (adjust to platform)
```

Also account for what leaves no trace on disk: exported environment variables, shell functions, port assignments, credentials injected at runtime.

For each item, record what it is, **why it exists in that form**, and the exact command to recreate it.

Where something fragile can be made durable in a minute, **do that instead of documenting the fragility** — move a temp data directory to a stable path, write an override into a gitignored config file. A note explaining how to rebuild a thing is strictly worse than the thing not needing a rebuild.

### 5. Write the handoff note

Write to the durable path from Inputs. Never inside the repo — a note sitting in the working tree gets swept into someone's `git add -A`.

### 6. Save durable memories

If file-based memory is available, save facts that outlive this session: environment gotchas, verified infrastructure facts, the agreed plan. One fact per file. Prefer updating an existing memory over creating a near-duplicate.

Keep this distinct from the note. The note is for the human tomorrow; memories are context for future sessions.

### 7. Report

Close with a short summary: repo state, what's open, where the note is, and the single next action. Keep it scannable — the user is leaving.

## Handoff note structure

```markdown
# <Project> — handoff notes, <YYYY-MM-DD>

## Where we are in one paragraph
[Goal, what actually happened today, what is and isn't deployed/merged.]

## Status
| Item | State | Notes |
|------|-------|-------|
| [PR / branch / ticket] | [Open / merged / blocked] | [SHA, blocker, staleness] |

Local checkout left on `<branch>` @ `<sha>`, [clean / with uncommitted X].

## Tomorrow's plan
1. [First action — specific and executable, not "continue work on X"]
2. ...

**Biggest risk:** [What could go wrong and why, if anything.]

**Deliberately deferred:** [Explicitly out of scope, so it isn't re-litigated.]

## Restoring the environment
[Copy-pasteable commands for anything ephemeral. Include why non-obvious
choices were made — a port, a flag, a version pin — so they aren't
"fixed" back into breakage tomorrow.]

## Expected state
[Baseline command and its known-good result, with numbers. Note which
failures are pre-existing so tomorrow's run can be compared, not
misread as new breakage.]

## Gotchas
[Traps that cost time today. Include the misleading symptom alongside the
real cause — the symptom is what gets searched for tomorrow.]
```

Drop sections that don't apply. A short accurate note beats a padded one.

## Key guidelines

- **Verify, don't recall.** Run the commands. State what was observed.
- **Never write secrets into the note.** No credentials, connection strings, tokens, or full hostnames for internal infrastructure. Describe or hash them instead — `staging and dev share one host, prod is separate` carries the finding without leaking the endpoint. The note lives outside the repo's protections.
- **Record why, not just what.** "Port 3307 because the default port's data directory is a newer format the installed server can't open" survives contact with tomorrow. "Use port 3307" gets overridden by someone being helpful.
- **Capture baselines as numbers.** "85 failures, all pre-existing, 70 from live S3 calls" lets tomorrow detect a regression. "Some tests fail" does not.
- **Name exactly one next action.** A prioritised list of six is a decision deferred, not a plan.
- **Distinguish verified from assumed.** If something wasn't checked, say so. False confidence in a handoff note is worse than an admitted gap.
- **Report blockers plainly**, including ones caused by today's work.

## What not to do

- Don't `git add -A` or `git commit -am` to "save" work — that is how churn and secrets get committed
- Don't push to a shared branch during housekeeping
- Don't leave the note inside the repo
- Don't write an optimistic summary; if the day ended mid-problem, the note should say so and describe the last known state
- Don't pad the note with what's already in git history or the project's docs — link or reference instead
