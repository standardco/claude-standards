Autonomous Support Triage Agent ("Gerald")
An LLM agent that triages a Help Scout inbox on a schedule: it categorizes new tickets, tags and routes them, leaves reasoning notes, asks customers for missing detail, drafts answers, nudges owners about stale tickets, and flags tickets that look ready to close.

It runs unattended — typically hourly — and reports what it did at the end of each run.

This repo is the distilled version of an agent that ran in production for several months. The interesting parts aren't the routing rules, which are specific to any given team. The interesting parts are the guard rails: the eligibility gates, the idempotency markers, the one-time caps, and the send-vs-draft split. Most of them exist because an earlier version misbehaved in a way that was annoying to clean up. See "Notes from production" at the end of SKILL.md.

Architecture
Three moving parts:

  ┌─────────────────┐
  │   Scheduler     │  cron-style trigger, hourly
  │  (task runner)  │  holds config + org-specific rules
  └────────┬────────┘
           │ invokes with prompt
           ▼
  ┌─────────────────┐
  │    SKILL.md     │  the agent's instructions (this repo)
  └────────┬────────┘
           │ calls tools
           ▼
  ┌─────────────────────────────────────┐
  │  MCP servers                        │
  │  • Help Scout    (required)         │
  │  • Slack bot     (required)         │
  │  • Task tracker  (optional, Step 4b)│
  │  • Docs search   (optional, Step 4) │
  └─────────────────────────────────────┘

The agent runtime is not special. This was built on Claude with MCP, but the skill is plain Markdown and any agent framework that can call the same tools and follow a long prompt will work.


Prerequisites
1. Help Scout MCP server (required)
Needs an API key with read/write access to the mailboxes you want triaged. The skill uses exactly these operations:

Read — list_conversations, get_conversation, list_threads Write — create_note, update_conversation_tags, update_conversation (status + assignee), create_reply

create_reply is the only tool that emails a customer. If you want to run with customer replies disabled entirely, withhold that one tool and the agent falls back to drafting — see "Staged rollout" below.
2. Slack bot (required)
Create a dedicated bot identity. Do not use a human's personal Slack token. Messages from this agent should be unmistakably attributable to automation, and a teammate should never receive an automated nudge that appears to come from a colleague.

Required scopes:

users:read.email is genuinely optional if you fill in the People table in SKILL.md with explicit Slack user IDs. Doing so is recommended regardless: it's faster, it doesn't depend on a scope an admin might not grant, and it's the only thing that works for teammates whose Slack account is registered to a personal email address rather than their work one. That case is more common than you'd expect and fails silently.

To find a user ID without the scope: open their profile in Slack → View full profile → ⋮ → Copy member ID. It starts with U. Note that the D… ID shown on a DM is the channel ID, not the user ID — you want the U….
3. Task tracker MCP (optional — Step 4b only)
Anything with a create-page/create-task operation. If your tracker's assignee field is a person reference rather than free text, you'll also need a user-lookup operation, and you should expect to maintain an override list for people whose tracker account uses a different email than their work address.

Omit this and skip Step 4b.
4. Documentation search (optional — Step 4 only)
Whatever your team actually uses: an internal wiki MCP, a docs site the agent can fetch, or a vector search endpoint. Without it, Step 4 degrades gracefully — the agent notes that no documentation was found and leaves the ticket for a human.
5. A scheduler
Anything that can invoke an agent with a prompt on a cron schedule. Hourly is a reasonable default. The skill is written to be safely re-runnable: every write is gated on an idempotency marker, so a missed run or a double run is harmless.


Setup
1. Copy SKILL.md into your agent's skill directory.

2. Fill in the Configuration section. Mailbox IDs, the People table, timezone, and your internal email domains. Nothing else in the skill needs editing to get a first run.

3. Write your assignment rules. This is the real work, and the part nobody can do for you. Open Step 3 and replace the rule skeleton with your team's actual routing. The structure that holds up:

1. Mailbox-level overrides   — "everything in mailbox X goes to <person>"
2. Topic overrides           — a subject area that always belongs to one person
3. Category + product rules  — mailbox.primary + `bug` → agent.backend
4. Per-mailbox catch-all     — so nothing leaves triage unassigned
5. Otherwise                 — unassigned

Two rules for writing rules. State precedence explicitly wherever two could both match — ambiguity in the rules becomes inconsistency in the routing, and you won't notice for weeks. And have the agent name which rule fired in its note, so a catch-all is visually distinct from a deliberate decision when you audit later.

4. Do a dry run. Point it at your inbox with write tools withheld and read the run summary. You're checking whether its categorizations match what you'd have chosen, and whether its routing lands on the right people. Expect to revise the rules two or three times.

5. Enable writes progressively. See below.

Configuring the org-specific parts
A pattern worth stealing: keep SKILL.md generic and put team-specific rules in the scheduler's prompt, layered as append-only blocks:

Run the `helpscout-ticket-triage` skill end-to-end.

ADDITIONAL RULE — <name> (applies in Step 3 assignment):
<rule text>
Precedence: <how this interacts with existing rules>
Scope: <which mailboxes>
(Added <date>.)

ADDITIONAL RULE — ...

This keeps the skill upgradeable — you can pull a new version of SKILL.md without losing your customizations — and it gives you a dated, readable audit trail of why the routing looks the way it does. Each block should state its precedence and scope explicitly, because rules accumulate and future-you will need to know which wins.


Known failure modes
The agent leaves the same note every hour. An idempotency marker is missing or its name changed. Every write must be gated on the absence of a specific marker string. If you rename a marker, existing tickets no longer match and the agent will re-act on all of them once.

Nudges go to nobody. Slack ID resolution failed. Check the run summary — the skill is written to report unresolvable assignees rather than guess. Usually a missing scope or a teammate on a personal email address. Fix it in the People table.

Tickets never get triaged. They're being auto-assigned before the agent sees them, and the "unassigned only" eligibility filter skips them. Common when a customer's email also holds an agent seat in your help desk. Add those seat IDs to your config and treat tickets assigned to them as unassigned.

Clarifications go to your own systems. An automated notification address is being treated as a customer. Confirm your internal domain list covers every address that can open a ticket — including no-reply and system-notification senders.

A stale ticket gets nudged forever. Gate 3 in Step 5a isn't firing. The check is for any prior Auto-nudge note regardless of age, not a recent one.


Design principles
Five things that made the difference between an agent people tolerated and one they relied on:

Every write is gated on a marker. Auto-triage, Auto-clarify, Auto-nudge, Auto-task, Auto-flag, Auto-emergency. These are guards, not decoration.

Bound outreach twice — per ticket and per run. Per-ticket caps stop repetition; per-run caps stop avalanches during an incident.

Skipped actions go in the run summary, not on the ticket. An agent that appends a detailed "here's why I skipped" note every hour buries the customer conversation within a day. One note is a record; six is vandalism.

Drafting is the default; sending is the exception. The one place this skill sends directly to a customer is narrowly scoped, excludes internal senders and stale threads, and is capped per run.

Never guess an identity. A nudge to the wrong person costs more trust than a nudge that didn't happen.
